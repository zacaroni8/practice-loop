## Phase 4 — Spec Decisions (in progress)

- **GUI framework: JavaFX.** Chosen over Swing for better modern docs/tutorials as a first GUI project.
- **Core practice-session loop: user-defined, not hardcoded.** Rather than Zac picking timer vs. checklist up front, the app lets its own end user (Zac, David, or anyone else using it) define what counts as a practice session for their own skill — e.g. a timer for open-ended practice, a checklist for a skill with discrete repeatable sub-tasks. This fits the app's two very different named users (piano drilling vs. video-editing tedium) better than one fixed session model would.
- **Reward system: none in v1.** Deliberately deferred rather than risk repeating Habitica's rigid-tiers-plus-loose-self-serve failure mode before the core tracking/scheduling loop is even proven out. Ship the tracker + forcing-function first; treat rewards as a stretch goal.
- **Forcing function: OS-level scheduled notifications.** Directly targets the named abandonment risk (practice falling out of schedule) by having the app itself push a reminder via the OS notification system, rather than relying on the user to remember to open it.

**Problem statement — first draft, needs rewrite.** Zac's first pass framed Practice Loop as a broad procrastination/ADHD tool for "elementary schoolers to CEOs" with the reward system as the core fix. Course-corrected: (1) this project is scoped to Zac and David specifically, not a general audience; (2) the reward system is out of v1 (see above), so the Problem statement can't lean on it as the mechanism — needs to justify the app on tracking + the notification forcing-function alone; (3) Zac correctly noted "plenty like this already exist" but didn't carry that acknowledgment, or the "why build it anyway" answer, into the actual paragraph — it needs to be written down explicitly, not left implicit. Rewrite pending, to be done next session.

**Scope re-litigated, reopened by Zac mid-Phase 4:** Zac pushed to bring the reward system back into v1 and initially proposed a full calendar-style scheduling UI. Pushed back hard on both. Calendar: scoped down correctly by Zac himself, from a full calendar-grid UI to "design the `Session` class so it's easy to bolt a calendar onto later, without building the calendar now" — a good instinct, kept as-is. Scheduling model decided: **planned sessions, not reactive.** Reactive "remind me after N days idle" fallback explicitly cut, not deferred — Zac's call, not revisited.

**Reward system — back in v1, with an actual mechanism this time.** Sharper version of the Habitica critique surfaced under questioning: it's not that the reward tiers are wrong in the abstract, it's that Habitica wants small, split-up rewards per task, but its UI (three flat lists — todo/dailies/habits) doesn't support the task-organization granularity that reward structure actually requires. Practice Loop's design: recommended reward number is **computed from real tracked session data** (logged minutes, not a flat guess), user can freely override it, optional max-per-minute or daily cap left as a later addition rather than a v1 requirement. Zac's reasoning for allowing free override rather than hard-enforcing: at this app's scale (Zac + David, two people who opted in on purpose) self-serving the reward defeats the user's own purpose for using the app — unlike Habitica's public, incentive-to-cheat scale, where enforcement matters more. Accepted as a deliberate, reasoned design choice, not an oversight.

**Scope tradeoff, resolved via a real hours recalculation and further cuts.** v1 now includes three brand-new technologies (JavaFX, SQLite, OS notifications) plus a reward system with real computation behind it. Checklist session type cut — v1 is timer-only ("focus sessions"); flagged as worth Zac double-checking against David's actual use case (his tedious work was described as discrete render/export steps, not open-ended time — timer-only may or may not still serve him well, Zac hasn't confirmed either way). Hours recalculated properly after an initial miscommunication (2–3 hrs/weekend vs. 2–3 hrs/day on weekend days): ~9 hrs/week weekday baseline + 4–6 hrs/weekend across the project's weekends works out to roughly 26–60 hours across 2–4 weeks, comfortably covering the original 25–35 hour estimate even with the added reward-system scope.
